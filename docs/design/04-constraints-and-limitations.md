# 04. 制約・既知の限界 — PixelForge

対象読者: 実装者。導入前に必ず目を通すこと。
関連: `02-conversion-pipeline.md`（各ステージの失敗時挙動）、`03-environment-and-setup.md`（モデルのライセンス確認）。

## 1. 法的・ライセンス面の制約（要事前確認）

| 項目 | 内容 | 状態 |
|---|---|---|
| 背景除去ライブラリ（`rembg`）自体のライセンス | MITライセンスであることを確認済み | ✅ 確認済み |
| 背景除去モデルの**重み**自体のライセンス | `rembg`が内部で使うu2net等のモデル重みは、`rembg`本体とは別プロジェクト（学術由来）が配布元であり、ライセンス条項が異なりうる。商用利用・再配布の可否を実装前に確認する必要がある | **未確認**（`03-environment-and-setup.md` §3） |
| 入力画像の著作権 | ユーザーが著作権保護されたキャラクター（既存アニメ・ゲームキャラ等）の画像をアップロードした場合、生成されるドット絵もその著作物の二次的著作物とみなされうる。ソフト側で技術的に検知・防止することはできない | 既知の限界（利用時の注意喚起に留める） |
| Agent Village本体の既存方針との整合 | `01-visual-concept.md`は「著作物のスプライト・タイルの流用は不可。オリジナルアセットを作る」という方針を明記している。本ツールは既存の版権スプライトを学習・複製する仕組みではなく、あくまで**利用者が用意した入力画像**を汎用アルゴリズムで変換するだけなので、その方針とは矛盾しない。ただし上記「入力画像の著作権」の論点は別途、利用者側の責任として残る | 整合ずみ（入力側の責任は利用者にある） |

## 2. 技術的な制約

| 項目 | 内容 |
|---|---|
| 入力画像の被写体数 | 単一キャラクターを想定。複数人物が写っている画像は、背景除去モデルがどれを主被写体とするか不定（最大の連結領域を採用する、等のルールをフォールバックとして設ける） |
| 処理時間 | CPU推論のため、1枚あたり数秒程度かかる想定（実機での計測は`03-environment-and-setup.md` §4の確認と合わせて実施すること） |
| 背景除去の精度限界 | 被写体と背景の色・コントラストが近い、輪郭が複雑（髪の毛の一本一本等）、半透明な素材、といった入力では誤検出が起きやすい。§3の入力画像ガイドラインで軽減する |
| 出力の忠実度 | ドット化・減色という不可逆な変換である以上、「元の写真に忠実」ではなく「元の特徴を残したレトロ風キャラクター」が出力される。写実的な再現は目的としない |
| 既定パラメータ（16×16・6色）の限界 | 帽子・翼など要素の多い実際のイラストで実機検証したところ、既定値では胴体から下がかなり潰れて見えることを確認した（顔・髪は`02-conversion-pipeline.md` §4のMAXCOVERAGE採用で良好）。グリッド24×24・色数8で改善、**32×32・色数10まで上げると腕・脚がはっきり判別できるレベルまで改善**することを確認済み。**要素が多いキャラクターでは既定値より大きめのグリッド/色数を推奨**する（UIでのプリセット案内をv2で検討） |
| 腕・脚が縮小時に消える/色が濁る | ユーザー報告により実機で確認。ダウンサンプリング（③）のアルファ処理を平均→最大値プーリングに、色の平均を透明ピクセル込み→アルファ加重に変更して緩和（`02-conversion-pipeline.md` §2③更新履歴）。ただし16×16グリッドでは依然として腕・脚が胴体と一体化しやすく、根本的にはグリッド解像度の限界が残る |
| 明るい色の服の縁が黒く滲む（premultiplied alpha） | ユーザー報告（白いラボコートのキャラクター）により実機で確認。原因は`rembg`の出力がPILモード上は`"RGBA"`（ストレートアルファ）と表示されるにもかかわらず、実データはpremultiplied alphaだったこと。`remove_background()`内でunpremultiply処理を追加して解消（`02-conversion-pipeline.md` §2①更新履歴）。暗い色の服では目立たなかったため発見が遅れた点は教訓として残す |
| 線画の多い服が全体的にグレーに濁る（ダウンサンプリングの平均処理） | 上記のpremultiplied alpha修正後も別のユーザー報告で発覚。ボタン・縫い目などの細かい黒線が白生地と1セルに混在すると、単純な平均ではグレーになってしまう。「暗い色がセルの少数派の場合のみ平均から除外する」方式に変更して解消（`02-conversion-pipeline.md` §2③更新履歴2）。目のような小さい色特徴を消してしまう別の失敗（モード方式）も経由したため、その試行錯誤も含めて記録している |
| 離れた部位が同じ色に割り当てられる | ユーザー報告により実機で確認（grid=64・色数10で、目の暗い赤と靴の焦げ茶が同じ色になった）。位置情報を無視した量子化が原因。バンド分割＋バンドごとのMAXCOVERAGE＋類似色優先統合に変更して解消（`02-conversion-pipeline.md` §2④更新履歴2）。同色の使用が複数部位にまたがる場合の一般的な保険として`fix_color_conflation`も残している |
| 口の抑制（②.5）が効かない場合がある | 「肌より暗い、顔下部中央の小さな塊」という位置・明暗ベースのヒューリスティックのため、口が肌と同程度の明るさで描かれている、前髪・マフラー等が肌色の基準取得帯にかかっている、2頭身から大きく外れる、といった入力では検出できないことがある。検出できなければ何もしない（フェイルソフト、無理に塗らない）。`02-conversion-pipeline.md` §2②.5参照 |
| 色白の肌等、背景とのコントラストが低い部位に透過の穴があく（`rembg`の低信頼度） | ユーザー報告（2026-08-16、business-character-c、脚部に穴）により実機で確認。`rembg`(u2netp)が背景と低コントラストな部位（色白の肌等）の内部に広く低いアルファ値（実測1〜50程度）を割り当てることがあり、④のダウンサンプリング（セル単位のMAX-pooling+閾値60）でセル全体がその閾値を下回ると透過の穴になる。`remove_background()`に、弱いアルファ(<60)かつ**元画像のクロマ`max(R,G,B)-min(R,G,B)`が15以上**（＝背景の無彩色グレーとは明確に異なる有彩色）の画素をオリジナル色で不透明化する補修を追加して解消（`02-conversion-pipeline.md` §2①更新履歴）。**既知の限界**: 白・黒・グレーなど無彩色の部位（白シャツ・黒靴等）で同種の低信頼度が起きた場合はこの補修の対象外（クロマが低くフィルタを通過しないため）。単純な背景色との距離判定（クロマでなくRGB距離）は、背景に落ちる影等クロマの低い無関係な要素まで誤って拾ってしまうため不採用にした経緯あり |

## 3. 入力画像のガイドライン・バリデーション

### 3.1 ハードバリデーション（実装済み・エラーで弾く）

> **更新履歴（実機検証済み）**: 当初は「強制バリデーションにはしない」方針だったが、実際にTポーズ（両腕を広げた構図）のイラストを入力したところ、自動トリミングが腕の横幅を基準に正方形を作ってしまい、胴体・脚が縦方向に圧縮された不自然な結果になることが実機で確認された。ユーザーから「正面立ちに合わない画像は無理に処理せずエラーにした方が設計しやすい」というフィードバックを受け、**この1点だけは強制バリデーションに変更した**。

| バリデーション | 実装 | 理由 |
|---|---|---|
| 検出したシルエットの幅/高さ比が閾値（既定0.75）を超えたら`UnsupportedPoseError`を送出する | `app/pipeline.py`の`crop_and_center()`。背景除去後のアルファのbounding boxで判定 | Tポーズ・腕を広げた構図は幅/高さ比が高くなる（実測: 合成の直立キャラは0.42、実際のTポーズイラストは0.77で閾値超過）。「無理に処理して悪い結果を返す」より「エラーにして別の画像を促す」方を選んだ |

エラーメッセージは「幅/高さ比が◯◯で上限◯◯を超えている。Tポーズ非対応、腕を下ろした正面立ちの画像を使うこと」を具体的に伝える（原因と対処法を明示する、`.claude`のCLAUDE.md的な文章方針と同じ考え方）。

**閾値0.75は初期値であり、より多くの実データで検証しながら調整する想定。**

### 3.2 ソフトガイドライン（推奨事項として表示、強制はしない）

| 推奨 | 理由 |
|---|---|
| 1枚の画像に写っているキャラクターは1体 | 背景除去モデルが主被写体を誤って選ぶのを防ぐ |
| キャラクターが画像の中央寄りにあり、画像全体の30%以上を占める | 小さすぎる被写体はダウンサンプリング後にディテールが失われやすい |
| 背景と被写体にある程度のコントラストがある画像 | 背景除去の精度が上がる（背景が多少ごちゃついていても、輪郭がはっきりしていれば問題ない、というユーザーの想定どおりの挙動になりやすい） |
| 極端な半透明・反射素材（ガラス細工等）を避ける | セグメンテーションが苦手とする素材 |
| **腕を下ろした正面立ちのポーズ** | §3.1のバリデーションを確実に通過するため。Tポーズ・腕を広げたポーズは通らない |

## 4. 失敗時の挙動方針

Agent Village本体の既存方針（`05-hooks-state-writer.md` §3.5「可視化はあくまで補助機能であり、失敗が本来の処理を止めてはならない」）と同じ考え方を踏襲する。

- 背景除去に失敗/低信頼度の場合: 警告を表示しつつ、元画像全体（背景除去なし）で後続処理を続行する。処理自体を止めない。
- 減色・書き出しに失敗した場合: エラーメッセージを明示し、パラメータ変更を促す（無言で失敗しない）。

## 5. スコープ外の入力（対応しない）

- 動画ファイル（静止画のみ対応、`00-overview.md` §3）。
- 透過PNGでない元画像でも動作するが、既に透過済みの画像を渡した場合は①の背景除去ステージをスキップできるようにする（二重処理を避ける）。
