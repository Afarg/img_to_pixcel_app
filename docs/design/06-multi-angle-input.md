# 06. 複数アングル入力への拡張 — PixelForge

対象読者: 実装者。
関連: `02-conversion-pipeline.md`（既存の単一画像パイプライン）、`05-agent-village-integration.md`（出力の受け渡し）、`../../ani_convert_app/docs/design/`（本ドキュメントの出力を消費する側）。

**実装状況**: 実装済み・実機検証済み（2026-07-28、斜め左右分割は2026-07-29追加）。`app/main.py`の`/api/convert`が正面(必須)+斜め(左向き/右向き、各任意)/横向き/後ろ向き(任意)の最大5枚を受け付け、`static/index.html`が5枠アップロードUIとフェーズ表示・バンドルZIPダウンロードを提供する。フェーズ1/2/3すべてを実データで実機検証済み（後述の更新履歴参照）。

---

## 1. 背景・目的

Agent Villageのキャラクターに歩行アニメーション（`docs/design/07-directional-animation-support.md`、agents_app本体側）を持たせたいという発展要望があり、そのためにはキャラクターの複数の向き（正面・斜め・横向き・後ろ向き）の絵が必要になる。

**重要な前提（技術的な壁）**: 1枚の写真には、その写真に写っている角度の情報しか存在しない。正面写真1枚から後ろ姿を機械的に生成することはできない（新しい視点を捏造することになり、決定論的な画像処理の範囲を超える。これをやるには専門的な生成AIが必要で、`01-architecture.md` §4で見送った理由がそのまま当てはまる）。

そのため本機能は「1枚の画像から4方向を自動生成する」のではなく、**利用者が持っている分だけ複数の入力画像を登録できるようにし、提供された分だけ処理する**、という方針にする。

> **更新履歴（ユーザーとの合意、2026-07-28・2回目）**: 「正面＋斜めをどちらも必須」という案を一度採用したが、**もっと段階的に使えるように**という要望を受け、以下の3フェーズ構成に組み直した。正面のみを必須の最小構成とし、斜め以降は段階的な追加とする。

## 2. 3フェーズ構成

| フェーズ | 入力 | 用途 |
|---|---|---|
| **フェーズ1（最小構成）** | 正面のみ | 正面画像1枚だけで完結する。この1枚は**Agent Villageの既存の「エージェントアイコン」機能にもそのまま使える**（`05-agent-village-integration.md` §1の既存アップロード仕様にすでに適合しているため、新しいバンドル形式もani_convert_appも介さず、既存の単一PNGアップロード経路がそのまま使える）。移動アニメーションは無し（静止画のまま、または正面を使い回す） |
| **フェーズ2（推奨）** | 正面＋斜め | 斜めを追加すると、Agent Village上での移動表示に斜めアングルが使われるようになる（`docs/design/07-directional-animation-support.md`）。**追加の手間が最小（画像1枚）で見た目の効果が一番大きいため、これを推奨構成とする。** 左右どちらか一方だけでもよい（もう一方は水平反転で代用）。 |
| **フェーズ3（フル）** | 正面＋斜め＋横向き＋後ろ向き | 4アングルすべて。横向き・後ろ向きが専用に用意されている方向は、斜めの水平反転ではなく専用の絵を使うため、より精度の高い見た目になる |

## 3. UI: 5つのアングルスロット

| スロット | 必須/推奨/任意 | 説明 |
|---|---|---|
| 正面 | **必須** | カメラ目線の見せ場（アイドル・会話時等）として使う基準アングル。**エージェントアイコン（一覧のサムネイル等）にも使う** |
| 斜め(左向き) | 推奨 | 3/4視点(左向き)。Agent Village上での左移動表示の基本アングルとして使う |
| 斜め(右向き) | 推奨 | 3/4視点(右向き)。右移動表示の基本アングルとして使う |
| 横向き | 任意 | 左右いずれか一方でよい（もう一方は水平反転で代用可能。第1世代ポケモン方式、`docs/design/01-visual-concept.md` §3.2で既に採用されている考え方） |
| 後ろ向き | 任意 | 上方向への移動時に使う |

- 各スロットは独立したファイルアップロード欄。**必須は正面のみ。** 斜め(左右)・横向き・後ろ向きは空でもよい（フェーズ1〜3のどの段階でも動作する）。
- どのスロットの画像も**本ツールが自動生成することはない**。利用者が用意した画像をそれぞれ独立に処理するだけ（§1の前提を参照）。
- 提供されなかったアングルは、後段のアニメーション変換ツール側でも生成しない（`../../ani_convert_app/docs/design/00-overview.md` §2で明記）。**「無い情報は作らない」を貫く。**
- UI上は斜め(左右)・横向き・後ろ向きのスロットに「推奨」「任意」のラベルを付け、フェーズ2（正面+斜め）を選ぶメリットを一言添える（例:「斜めを追加すると移動時の見た目が自然になります」）。

> **更新履歴（ユーザーとの合意、2026-07-29）**: 「斜め」1枠（左右反転で使い回す想定）を「斜め(左向き)」「斜め(右向き)」の2枠に分割した。左右非対称なデザイン（小物を片手に持っている、髪型が左右非対称等）のキャラクターは、水平反転による使い回しでは実際の見た目と食い違うため。片方だけの入力にも引き続き対応し（もう片方は従来どおり水平反転で代用）、両方入力すれば非対称なキャラクターも正確に表示できる。「横向き」スロットは元々この「片方だけでもよい・反転で代用」という設計だったため、その考え方を斜めにも広げた形になる。横向き・後ろ向き自体の左右分割は今回のスコープ外（ユーザーからの要望は斜めのみ）。

## 4. パイプラインへの適用

各スロットの画像は、`02-conversion-pipeline.md`で定義した①〜⑥の処理を**アングルごとに独立して**適用する。処理そのものに変更はない。

## 5. パレットの一貫性（新しい技術的課題）

複数アングルを別々に量子化すると、アングルごとに微妙に異なる代表色が選ばれ、「後ろ向きだけ服の色が違う」といった不整合が起きる。

**対応方針**: 正面画像を基準とし、そのパレットを他アングルにも共通適用する。

- ①〜③まではアングルごとに独立処理（背景除去・トリミング・ダウンサンプリングは各画像固有の内容に依存するため）。
- ④の減色ステージのみ、正面画像に対して`quantize_colors()`（バンド分割＋バンドごとのMAXCOVERAGE＋類似色優先統合、`02-conversion-pipeline.md` §2④）を実行して確定パレットを得たあと、他アングル（提供されていれば斜め左右・横向き・後ろ向き）の画像は`quantize_colors(..., palette_source=<正面の量子化済み画像>)`で同じパレットに合わせて量子化する。
- 正面が用意されていない、という状況は起こらない（正面は唯一の必須スロットのため）。**正面だけが常に「パレットの基準」であり、他アングルが無い場合（フェーズ1）はそもそも統一すべき対象が無いので問題にならない。**

> **更新履歴（実機検証で発見・修正済み、2026-07-28）**: 実装時、`quantize_colors(..., palette_source=...)`の経路を初めて実際に通したところ、`bad mode for palette image`というエラーで500が返ることが判明した。原因はPillowの`Image.quantize(palette=...)`がパレットモード（`"P"`）の画像を要求する仕様であるのに対し、`quantized_reference`（RGBA→RGB変換のみ）をそのまま渡していたこと。`app/quantize.py`で、渡す前に一度`source_rgb.quantize(colors=<実際の色数>)`でパレットモード画像に変換してから使うよう修正し、フェーズ2（正面+斜め）・フェーズ3（4アングル全て）の両方で実データ・実ブラウザ操作にて再検証し解消を確認した。
>
> **更新履歴（実機検証で発見・修正済み、2026-07-29）**: 上記の修正後も、④.5の衝突チェック保険処理（`fix_color_conflation()`、`02-conversion-pipeline.md` §2④.5）が`app/pipeline.py`の`convert()`で**`palette_source`使用時にも無条件に実行されていた**ため、共通パレットのはずが実際にはアングルごとにズレてしまっていた（`colors=8`指定で正面13色・斜め20色、ユーザー報告「待機中と歩行中で肌色が違う」で発覚）。`palette_source is None`の場合（パレットを新規に確定させる正面ビュー）にのみこの保険処理を実行するよう修正し、正面と斜めで共有パレットが（輪郭に関係しないごく僅かな黒の差1色を除き）完全一致することを実機確認した。
>
> **更新履歴（実機検証で発見・修正済み、2026-07-31）**: 上記の修正（④.5を`palette_source is None`時のみに限定）の副作用として、**斜めビュー側は衝突チェックの保険が一切効かなくなり、別種の衝突（顔のハイライト色が離れた胴体の1pxに誤って現れる）を素通ししてしまう**バグが新たに見つかった。ユーザー提供の実データ（正面+斜め左+斜め右の3枚、蝙蝠羽根キャラとは別の青髪キャラ）で実際にパイプラインを走らせて再現・実測: `grid_size=32, colors=8`で、斜め左右の両方に、正面には存在しない頬のハイライト色（`RGB(209,167,176)`、本来y=11-13の狭い範囲のみ）が胴体側のy=23に1pxだけ誤って出現していた（8倍拡大画像で肩付近のピンクの粒として視認・確認）。原因は`quantize_colors()`の`palette_source`経路が完全に無方向・無部位のRGB最近傍マッチングのため、斜めビュー（正面とは別々に生成されたAI画像で厳密なRGB値が異なる）の胴体ピクセルが、たまたま顔ハイライト色の方に最も近くなってしまうこと。
>
> 対応として`fix_color_conflation()`をそのまま斜めビューに適用することは**しなかった**: `grid_size∈{32,64}`×`colors∈{6,8,10}`の6パターンで検証した結果、同関数の判定条件（縦方向の広がりが画像高さの30%を超えたら分割、分割に使う"隙間"の大きさは問わない）は、ジャケットの青のような**本来1つの連続した領域**（内部にわずか2行程度の隙間があるだけ）まで「衝突」と誤判定するケースが多数見つかり、これをそのまま使うと赤ピクセルは直っても別の場所（ジャケットの色の不自然な分裂等）に新しい見た目崩れを生みかねないと判断した。
>
> 代わりに、ユーザー提案（「部位ごとに閾値を調整できないか」）を受けて、**`quantize_colors()`自身が既に使っている5分割の水平バンド（頭/首/胴/脚/足の代理）を衝突検知の単位にする**新関数`fix_stray_band_pixels()`（`app/quantize.py`）を実装した: 各色について「最も多く存在するバンド（ホーム）」を求め、①ホーム以外に存在するバンドがちょうど1つだけ、②そのバンドがホームから2つ以上離れている、③そのバンドの画素数が2px以下、④ホームがそのバンドの4倍以上の画素数を持つ、の4条件をすべて満たす場合だけを「浮遊ピクセル」と判定し、`pre_quantize_source`（量子化前の縮小画像）の実際の色を参照した上で、**新しい色を作らず、その斜めビューの量子化画像に既に存在する色の中から最も近いものに置き換える**（共有パレットの色数を絶対に増やさない）。「他バンドがちょうど1つだけ」という条件が、輪郭の暗色や共通のハイライト白のように**意図的に全身へ薄く再利用されている色**（3バンド以上に分散）を誤って巻き込まないための要になっている。
>
> 検証: 上記6パターン全てで実際に`pipeline.convert()`を通し、①既知の頬ハイライト色の漏れpxが消え、正面と完全に同じ範囲(y=11-13, 7px)に収まること、②斜めビューの色数が正面の色数を一度も超えないこと（共有パレットの前提を維持）、③修正後に残る"浮遊"判定が皆無であること、を確認した。`colors=6`の設定ではそもそもこの漏れが発生しないことも実測済み（8倍拡大画像で目視確認）で、閾値が過検知していないことも合わせて確認済み。既存のスモークテスト（`scripts/test_pipeline.py`、正面のみ・`palette_source`不使用の経路）も無変更で通ることを確認した。

## 6. 後段ツールへの受け渡し形式（キャラクターアセットバンドル）

`ani_convert_app`（まばたき・歩行差分の生成）に渡すため、単一PNGではなく**マニフェスト付きのバンドル**として出力する。**ただしフェーズ1（正面のみ）の場合は、バンドルを介さず既存の単一PNGアップロード経路（`05-agent-village-integration.md`）をそのまま使ってよい** — バンドル形式が必要になるのは、まばたき・歩行アニメーションを持たせたい（フェーズ2以降に進みたい）場合のみ。

```
<character-id>/
├─ manifest.json
├─ front.png               # ⑥まで通した最終ピクセルアート（必須）
├─ front.pre.png           # ①②の後、③（ダウンサンプリング）前の中間画像（アルファ付き、高解像度）
├─ diagonal_left.png       # 推奨（フェーズ2以降、提供されていれば存在）
├─ diagonal_left.pre.png   # 推奨
├─ diagonal_right.png      # 推奨（片方だけの提供でも可。両方あれば両方存在）
├─ diagonal_right.pre.png  # 推奨
├─ side.png                # 任意（フェーズ3）
├─ side.pre.png            # 任意
├─ back.png                # 任意（フェーズ3）
└─ back.pre.png            # 任意
```

`*.pre.png`（背景除去・トリミング済みだが縮小前の画像）を残す理由: `ani_convert_app`がまばたき用の目の位置検出を行う際、最終的な16×16等の極小ピクセルアートでは検出精度が出ない。縮小前の解像度で顔・目のランドマークを検出し、その座標を③のダウンサンプリング倍率で変換すれば、最終ピクセルグリッド上のどのマスが目にあたるかを正確に特定できる（`../../ani_convert_app/docs/design/02-generation-pipeline.md` §2参照）。

`manifest.json`の例（フェーズ2: 正面+斜め両方の場合）:

```jsonc
{
  "characterId": "code-reviewer",
  "gridSize": 16,
  "outputSize": 64,
  "colors": 6,
  "views": {
    "front":          { "final": "front.png",          "pre": "front.pre.png",          "scale": 4.0, "cropBox": [12, 8, 148, 144] },
    "diagonal_left":  { "final": "diagonal_left.png",  "pre": "diagonal_left.pre.png",  "scale": 3.9, "cropBox": [11, 7, 149, 145] },
    "diagonal_right": { "final": "diagonal_right.png", "pre": "diagonal_right.pre.png", "scale": 3.9, "cropBox": [13, 7, 150, 145] }
    // フェーズ1なら diagonal_left / diagonal_right キー自体が存在しない。片方だけ提供した場合はそちらのキーのみ存在する。フェーズ3なら back / side も同様のキーを持つ
  }
}
```

- `scale`・`cropBox`: `*.pre.png`上の座標を最終`*.png`上の座標へ変換するための係数（`ani_convert_app`側で使用）。
- `views`に`front`以外のキーが存在しない場合はフェーズ1（正面のみ）であることを意味し、`ani_convert_app`は他アングルの生成処理をスキップする。`front`だけは必須スロットのため、欠けることは想定しない。

## 7. Agent Villageのエージェントアイコンとしての利用（フェーズ1の位置づけ）

正面画像（`front.png`）は、Agent Village本体の既存機能（サイドバーのエージェント一覧のサムネイル、`public/js/hud.js`の`thumb`要素）にもそのまま使える。既存の単一PNGアップロード仕様（正方形・16〜128px・300KB以下、`05-agent-village-integration.md` §1）に元々適合させているため、**フェーズ1（正面のみ）の利用者は、本ドキュメントの複雑なバンドル機構を一切意識せず、PixelForgeで正面画像を1枚作って、既存の「見た目を差し替える」欄にアップロードするだけで完結する。** 斜め・横向き・後ろ向きを追加したくなった時点で、初めてバンドル形式・`ani_convert_app`・Agent Village側の新規エンドポイント（`docs/design/07-directional-animation-support.md`）が必要になる、という段階的な体験にする。
